# Spec 01 — Real PWA: manifest, splash, icons, install invite, push notifications, staged rollout

- **Owner area:** PWA / service worker / push (see [README.md](README.md))
- **FR range:** FR-050 – FR-059
- **ADRs:** [ADR-019](../../decisions/ADR-019-custom-service-worker-inject-manifest.md) (custom service worker), [ADR-020](../../decisions/ADR-020-web-push-and-staged-rollout.md) (Web Push + staged rollout) — both *Proposed*
- **Migration:** `0013_pwa.sql` (provisional number)
- **Status:** Draft for implementation, 2026-10-28

## 1. Summary

info.bisericabetel is technically installable today (manifest + Workbox service worker), but nothing invites visitors to install it, iOS users get a blank white splash and a generic icon, and there is no way to tell members about a new event once they close the page. This spec turns the hub into a complete PWA on iOS and Android — manifest, icon set (including maskable and Apple touch icons), splash screens, a custom service worker — adds a platform-aware, one-time **install invite** (native prompt on Chromium Android, illustrated "Share → Add to Home Screen" guide on iOS, "open in your browser" hint inside WhatsApp/Facebook/Instagram), and **Web Push notifications for new events** (VAPID, opt-in only, scoped to the visitor's site and language, deduplicated per event). Everything ships behind a **rollout switch** (`off` → `beta` testers via an opt-in link → `all`) controlled from a new super-admin page, so the owner can go live quietly with a handful of testers and later "turn it on" for everyone, once.

## 2. Goals / Non-goals

**Goals**
- G1. Pass the installability bar on Chrome/Edge/Samsung Internet (Android) and look native when added to the Home Screen on iOS 16.4+ (icon, splash, standalone display, status bar).
- G2. One friendly, non-intrusive install invite per visitor, platform-specific, remembered when dismissed; plus a permanent, discreet entry point for people who change their mind.
- G3. Push notifications for *new events* only, strictly opt-in, scoped to the site view and language the visitor uses, one notification per event, with cleanup of dead subscriptions and admin visibility.
- G4. Staged rollout controlled by a super-admin: silent by default, visible to beta testers through an opt-in link, then to everyone; the invite can be re-armed once ("campaign") if the owner wants to re-invite.
- G5. Keep the "always latest version within one page load" guarantee of ADR-013.

**Non-goals**
- Manual/ad-hoc notifications for arbitrary content and per-item event *reminders* (the roadmap's Phase 3 "Push notifications" item) — only the hook points are prepared; a follow-up spec can add them. The automatic new-event notification in this spec is Phase 2 work and supersedes the "new content alert" half of that roadmap item (§12 rewrites it).
- Per-user accounts, notification preferences beyond site + language, or any identity. Subscriptions are anonymous.
- Email/SMS channels, native apps, app stores (no TWA/PWABuilder).
- Offline authoring or offline support for `/admin/*` (stays out of the service worker, as today).
- Manifest `shortcuts` per site: sites are data, the manifest is static at build time — deferred (see Open questions).
- SEO head tags, canonical URLs, feeds, sitemap: owned by specs 02 and 03. This spec only adds their paths to the service-worker denylist.

Platform facts this design relies on (verified 2026-10-28):
- **iOS/iPadOS:** Web Push exists since 16.4 and only for web apps added to the Home Screen whose manifest `display` is `standalone` or `fullscreen`; the permission prompt must be triggered by a user gesture; Badging API available. In a Safari *tab* the Push/Notification APIs are not usable, so the app must guide the user to install first. Since iOS 26, "Add to Home Screen" opens sites as web apps by default (toggle "Open as Web App", on by default). Third-party iOS browsers (Chrome, Firefox, Edge) can add Home Screen web apps too since 16.4, through their own share/menu. In-app browsers (Facebook/Instagram WKWebView, WhatsApp/Gmail SFSafariViewController) cannot add to the Home Screen. A Home Screen web app has **its own storage**, separate from Safari (localStorage does not carry over on install). Safari 18.4+/iOS 18.4+ support *Declarative Web Push* (`"web_push": 8030` JSON payload displayed without a service worker; standard push is the fallback).
- **Android (Chromium: Chrome, Edge, Samsung Internet, Brave, Opera):** `beforeinstallprompt` fires when the manifest has `name`/`short_name`, 192 + 512 px icons, `start_url`, `display` in {`standalone`,`fullscreen`,`minimal-ui`,`window-controls-overlay`}, HTTPS, and after some engagement (a click and ~30 s on the page). Screenshots + `description` enable the richer install sheet. Splash screen is built from `background_color`, the icon and `name`. Maskable icons must keep their content in the central safe zone (circle of 80 % of the icon size). Firefox Android installs from its menu (no `beforeinstallprompt`) and supports push. WhatsApp Android opens links in a Chrome Custom Tab (no install prompt; "Open in Chrome" from the ⋮ menu); Facebook/Instagram Android use a WebView.
- **Web Push protocol / `web-push` npm:** VAPID keys generated once and reused; `sendNotification(subscription, payload, { TTL, urgency, topic })`; push services answer **404/410 for dead subscriptions** (delete them), 413 for oversized payloads (keep payloads well under 4 KB), 429 for rate limiting; errors expose `statusCode`/`body`. Apple's push service rejects placeholder VAPID subjects — use a real `mailto:` or `https:` subject.

## 4. User flows

### Flow A — Public visitor, Android (Chromium), rollout `all`
1. Member opens `/centru` from a QR code or WhatsApp link (Chrome Custom Tab → page works; the invite is not shown there because `beforeinstallprompt` never fires in a Custom Tab; instead, after the engagement delay, the invite offers "Deschide în Chrome" guidance).
2. In Chrome proper: after the content has rendered and ~8 s of dwell (or a scroll), a compact sheet slides up from the bottom: icon, "Instalează Betel Info pe telefon", one line of benefit, buttons **Instalează** (primary) and **Nu acum**.
3. **Instalează** calls the captured `beforeinstallprompt.prompt()`; the native sheet appears. Accept → `appinstalled` → `pwa_install` analytics event, invite marked done. Dismiss → invite marked dismissed (never shown again for this campaign).
4. Next launch from the Home Screen: Android splash (black, icon, "Betel Info"), app opens standalone to `/`, which restores the remembered site (FR-005). `pwa_launch` analytics event once per 30 min.
5. Below the feed (once, dismissible) a card: "Vrei să afli când apare un eveniment nou la Betel Centru?" with **Activează notificările**. Tap → `Notification.requestPermission()` → subscribe → stored server-side with `site=centru`, `locale=ro`. A bell icon in the footer now reads "Notificări active" and lets the member turn them off.
6. An admin publishes a card with a start date next Saturday → within the debounce window the member receives "Eveniment nou · Betel Centru — Seară de tineret · sâmbătă, 7 noiembrie, 19:00 · Sala mare" (the location line only when the card has one, spec 07). Tap → app opens the item page `/i/<id>?n=<notificationId>` (spec 03's per-item route), which records the open and shows the event.

### Flow B — Public visitor, iOS Safari
1. Same entry. Safari tab: no push APIs, no native prompt. After the dwell delay the invite sheet appears with **Arată-mi cum** / **Nu acum**.
2. **Arată-mi cum** opens an illustrated 3-step guide: (1) tap the Share button (icon drawn inline, bottom bar), (2) choose "Adaugă pe ecranul principal" (iOS 26: leave "Deschide ca aplicație web" on), (3) tap "Adaugă". A footnote covers the case where the option is missing: "Dacă nu vezi opțiunea, deschide pagina în Safari (butonul busolă din colțul din dreapta-jos)" — this is the SFSafariViewController case (WhatsApp, Gmail), which is not detectable from the user agent.
3. The guide is dismissible; the invite is then marked done. A discreet footer link "Instalează aplicația" stays available (Safari tab only) for later.
4. From the Home Screen the app opens standalone with the generated splash (light or dark per `prefers-color-scheme`), status bar integrated. Storage is new here (iOS keeps it separate from Safari): site is taken from `start_url` → `/`; the member picks the site once more; nothing else is lost.
5. In standalone mode the push opt-in card is shown (stage `all`, or stage `beta` — see Flow D) and works like Flow A.

### Flow C — In-app browser (Facebook / Instagram / TikTok WebView, any platform)
1. UA matches an in-app WebView token (`FBAN`, `FBAV`, `FB_IAB`, `Instagram`, `BytedanceWebview`, `Line/`, `Twitter`, or iOS UA without the `Safari/` token).
2. The invite (if due) shows a single step: "Pentru a instala, deschide pagina în Safari / Chrome" with the platform's gesture (iOS: "⋯ → Deschide în Safari"; Android: "⋮ → Deschide în Chrome"), and a **Copiază linkul** button as a fallback. No push opt-in is offered inside in-app browsers.

### Flow D — Beta tester (rollout `beta`)
1. Super-admin sets stage to **Testeri** on `/admin/pwa` and copies the tester link shown there: `https://info.bisericabetel.com/?pwa=beta` (built from `PUBLIC_BASE_URL`; any hub path works, e.g. `/centru?pwa=beta`).
2. Tester opens the link; the app stores `betel-pwa-beta=1` and, from then on, behaves as stage `all` on that browser. The `?pwa=beta` parameter is left in the URL on purpose (so the "open in Safari" handoff from an in-app browser keeps it). `?pwa=off` clears the flag.
3. iOS caveat: after installing, the Home Screen app has fresh storage, so the beta flag is gone. Rule: in stage `beta`, a **standalone** launch is always treated as beta-eligible (only testers were invited to install; a stray manual install is harmless).
4. Testers' subscriptions are tagged `channel = 'beta'`. The admin "Trimite o notificare de test" button targets exactly those.

### Flow E — Admin: going live and turning it on for everyone
1. Deploy with VAPID keys set in CapRover (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`). Stage defaults to **Oprit**: nothing is visible publicly; the API still accepts nothing push-related except `GET /api/pwa/config`.
2. `/admin/pwa` (super-admin, nav "Aplicație"): choose **Testeri**, share the link, watch "Abonamente active" grow, send a test notification, publish a real event and check the log row (recipients, sent, failed, opens).
3. Choose **Toți vizitatorii**. Every visitor now gets the one-time invite and the opt-in card.
4. Later, optionally, **Reinvită pe toți** bumps the campaign number: visitors who dismissed campaign 1 see the invite once more. Each click is audit-logged.

### Flow F — Admin: publishing an event (unchanged UI, new side effect)
1. Admin publishes a Card that has `data.startDate` today or later (REST toggle, edit form, or an AI agent via MCP).
2. The API enqueues one notification for that item (unique per item — re-publishing later never notifies again), due after the debounce window (default 10 min) and outside quiet hours (default 21:00–08:00 Europe/Bucharest).
3. If the admin unpublishes, deletes or removes the start date within the window, or the start date has already passed when the row comes due, the queued row is cancelled at send time.
4. The log on `/admin/pwa` shows the row moving from "În așteptare" to "Trimisă (123 trimise, 2 eșuate)". Dead subscriptions returned 404/410 by the push services are deleted immediately.
5. If the super-admin sets the rollout stage to `off` while rows are queued, nothing is sent; the rows wait. Turning the stage back on sends the rows that are still valid and younger than 24 h (counted from `send_after`); older ones are cancelled as stale.

### Flow G — Crawler / AI agent
Not applicable; the manifest, icons and `sw.js` are static assets. Spec 03 owns `robots.txt` and may disallow `/sw.js` or not — no requirement from this spec.

## 5. Requirements

Each requirement is testable; "must" is normative.

- **FR-050 — Complete installable shell.** The hand-written `<link rel="manifest">` in `index.html` must be removed so the built page carries exactly one manifest link (the one vite-plugin-pwa injects). The app must ship a manifest with `id: '/'`, `scope: '/'`, `start_url: '/'`, `lang: 'ro'`, `display: 'standalone'`, `name`, `short_name`, `description`, `theme_color`, `background_color`, `categories`, at least two `screenshots` with `form_factor: 'narrow'`, and icons: 64, 192, 512 px `purpose: any`, 512 px `purpose: maskable` (content inside the central 80 % circle), plus `apple-touch-icon` 180 px (opaque). `index.html` must carry `apple-touch-icon`, `apple-touch-startup-image` links covering current iPhone/iPad sizes in light and dark variants, `mobile-web-app-capable`, `apple-mobile-web-app-capable`, `apple-mobile-web-app-title`, `apple-mobile-web-app-status-bar-style`, and `viewport-fit=cover` with safe-area padding on the hero header and footer. Acceptance: Chrome DevTools "Application → Manifest" shows no installability warnings; Lighthouse manifest audit passes; on an iPhone the Home Screen app opens with the Betel splash, no white flash, and the status bar matches the theme.
- **FR-051 — Custom service worker.** The service worker must be built with `injectManifest` from `packages/app/src/sw.ts` (ADR-019), keep `autoUpdate` semantics (`skipWaiting` + `clientsClaim`, `cleanupOutdatedCaches`), precache the app shell (`js,css,html,ico,png,svg,woff,woff2`, excluding splash screens and screenshots), serve navigations from the precached `index.html` except for `/admin*`, `/s/*`, `/api/*`, `/uploads/*`, `/mcp*`, `/health`, `/robots.txt`, `/sitemap.xml`, `/feed.xml`, `/*/feed.xml`, `/llms.txt` (denylist owned here, paths provided by specs 02/03/06; the per-item SPA route `/i/:itemId` from spec 03 is **not** denylisted — it is part of the shell. Server-rendered HTML (ADR-022) serves first loads, crawlers and non-SW clients; navigations controlled by the service worker get the precached shell for `/`, `/:siteSlug` and `/i/:itemId` alike, and the SPA fetches data. Only server-only routes — `/s/*`, `/robots.txt`, `/sitemap.xml`, `/feed.xml`, `/*/feed.xml`, `/llms.txt`, `/uploads/*` — are denylisted), add matching Vite `server.proxy` entries for `/robots.txt`, `/sitemap.xml`, `/feed.xml`, `/llms.txt` (and, closing a known leftover, `/s` and `/uploads`) so those server routes work on `:5173`, apply `NetworkFirst` (5 min) to `GET /api/*` and `CacheFirst` (30 days, 60 entries) to `/uploads/*` images, and implement `push`, `notificationclick` and `pushsubscriptionchange`. Acceptance: existing `expired-content`, `home` and `admin-*` Cypress specs still pass; a production build serves `/s/abc`, `/feed.xml` and `/robots.txt` from the server, not from the SPA shell, while `/i/<id>` is served from the shell; a push with the exact payload in §6.4 shows a notification whose click opens/focuses the app at `notification.navigate`.
- **FR-052 — One-time, platform-aware install invite.** When rollout allows (FR-053), the visitor is not in standalone mode, and no decision is recorded for the current campaign, the hub must show one invite after the feed has rendered and the visitor has either dwelled 8 s or scrolled. Variants: (a) Chromium with a captured `beforeinstallprompt` → native prompt; (b) iOS browser (Safari or other) → illustrated share-sheet guide; (c) Android without a captured event (Firefox, Custom Tab, WebView) → menu guide with "open in Chrome" hint; (d) in-app browser → "open in Safari/Chrome" hint + copy link; (e) desktop → no invite. "Nu acum", closing the guide, accepting or dismissing the native prompt all record the decision in `localStorage` (`betel-pwa-invite`), and the invite is never shown again for that campaign. A footer link "Instalează aplicația" must remain available whenever variant (a)–(c) applies and the app is not standalone. The invite must not cover the content feed permanently, must be dismissible with one tap, must respect `prefers-reduced-motion`, and must use `t()` keys for every string.
- **FR-053 — Staged rollout and admin switch.** A super-admin page `/admin/pwa` (nav "Aplicație") must expose the rollout stage (`off` | `beta` | `all`, default `off`), the beta link, a "re-invite" action that increments the invite campaign, push settings (debounce minutes, quiet hours), and the push configuration status. The public endpoint `GET /api/pwa/config` must return the stage, campaign and VAPID public key (the latter only when stage ≠ `off` and keys are configured). Eligibility on the client is `stage === 'all' || (stage === 'beta' && (betaFlag || standalone))`; the beta flag is set by `?pwa=beta` and cleared by `?pwa=off`. Every settings change is audit-logged (`pwa.settings.update`, `pwa.invite.campaign`).
- **FR-054 — Push opt-in / opt-out.** When eligible and push is supported in the current context (`'serviceWorker' in navigator && 'PushManager' in window && 'Notification' in window`, not an in-app browser), the hub must offer a one-time, dismissible opt-in card after the feed and a persistent footer bell control. Permission is requested only from a tap on the opt-in button. On iOS in a browser tab, the card instead explains that notifications need the installed app and opens the install guide. Subscribing posts `{ subscription, site, locale, channel, platform, standalone }` to `POST /api/push/subscriptions`; unsubscribing calls `PushSubscription.unsubscribe()` and `DELETE /api/push/subscriptions`. Changing site or language while subscribed re-posts the subscription (upsert by endpoint). Denied permission hides the controls and shows nothing else. The app re-posts (refreshes `last_seen_at`) at most once per 24 h on launch while subscribed, and immediately — with full metadata — when the browser's current subscription endpoint differs from the one recorded in `betel-pwa-push` (the repair path for a `pushsubscriptionchange` the server could not resolve, FR-057).
- **FR-055 — What fires a notification and when.** A notification is enqueued exactly once per content item when a **Card** with a non-empty `data.title` and `data.startDate` ≥ today (Europe/Bucharest) transitions to `published` through any path (`POST …/publish`, `PATCH` with `state`, remote MCP `publish_card`). Richtext, Poster and Video items, edits of already-published items, items without a start date, and past-dated items never notify. Dedupe is enforced by a partial unique index on `push_notifications.content_item_id` (`kind = 'new_event'`). The row becomes due after the debounce window and outside quiet hours; at send time the item must still be `published`, not expired, a Card with a non-empty title and a `data.startDate` that is **not past** (`startDate ≥ today` in Europe/Bucharest — a future start date is of course fine), otherwise the row is cancelled (`cancel_reason` `unpublished` | `past` | `no_date`). While the rollout stage is `off` no row is claimed: queued rows wait, and when the stage returns to `beta`/`all` the poller sends those whose `send_after` is less than 24 h old and still pass the re-validation, and cancels the rest (`cancel_reason = 'stale'`). A claimed (`sending`) row carries a lease (`claimed_at`); a row still `sending` 10 min after its claim is treated as crashed and re-queued (at most 3 attempts, then `status = 'failed'`). Sending happens off the request path, with bounded concurrency, and never blocks or fails the publish request.
- **FR-056 — Targeting, language and content of the notification.** A subscription with `site_slug = S` receives an item iff the item would appear on view `S` (`exclusive_site = S`, or `exclusive_site IS NULL` and (`sites = '{}'` or `S = ANY(sites)`)); a subscription with `site_slug IS NULL` (all-sites view) receives every non-exclusive item. Group scope is not applied (BR-005 gap, consistent with `GET /api/content`). Text is built per subscription locale: title from `content_translations` for that locale with Romanian fallback; the "when" text from `formatEventWhen()` in `packages/shared/src/event-time.ts` (spec 04: `data.startDate` + optional `data.startTime`, date-only when the time is absent); the "where" text from `readLocation()` (`packages/shared/src/event-location.ts`, spec 07) on the locale-merged data (translated value with Romanian fallback), appended to the body after the when text as `" · {location}"` when present — e.g. `Seară de tineret — sâmbătă, 7 noiembrie, 19:00 · Sala mare`; the site name stays in the title and `data.location` never changes targeting; UI phrases from `ui_translations` keys `pwa.push.newEvent.title` / `pwa.push.newEvent.titleAll` with Romanian fallbacks. The click URL is the per-item page `/i/<itemId>?n=<notificationId>` (spec 03), always absolute via `absoluteUrl()` (spec 03 FR-066: `PUBLIC_BASE_URL` is required in production and defaults to `http://localhost:3100` in development; there is no relative-URL case). The click URL travels in exactly one payload field, `notification.navigate` (§6.4); the service worker, Safari's declarative push and the tests all read that field. The public app must record `notification_open` (with `itemId` and `url = notificationId`) whenever a public route loads with `?n=`, then drop `n` from the URL. Payload ≤ 2 KB (unaffected by the ≤ 70-character location).
- **FR-057 — Subscription lifecycle and cleanup.** Subscriptions are deleted immediately on push-service status 404 or 410; other failures increment `fail_count` and set `last_failed_at`, and a subscription with `fail_count ≥ 5` whose last failure is older than 7 days is deleted. A daily sweep deletes subscriptions with `expiration_time < now()` or `last_seen_at` older than 180 days. `pushsubscriptionchange` in the service worker re-subscribes with the VAPID key from `/api/pwa/config` and posts `{ subscription, replacesEndpoint: <old endpoint> }` to `POST /api/push/subscriptions` **without** site/locale/channel/platform/standalone (a service worker has no access to the app's `localStorage`); the server recovers that metadata from the row keyed by `replacesEndpoint`, copies it onto the new row and deletes the old one. If no row matches `replacesEndpoint` the server answers 404 and stores nothing; the app repairs it on its next launch (FR-054: when `pushManager.getSubscription().endpoint` differs from the endpoint in `betel-pwa-push`, it re-posts the current subscription with full metadata and updates the local record). Unsubscribing in-app deletes the row; revoking at OS level is caught by the next 404/410.
- **FR-058 — Admin visibility.** `/admin/pwa` must show: active subscriptions (total and by site, platform, channel, locale), subscriptions created in the last 7/30 days, the notification log (newest first, paginated: date, event title, status with cancel reason, recipients, sent, failed, opens), a "Trimite o notificare de test către testeri" button (channel `beta` only, audit `pwa.push.test`), and a "Anulează" action on queued rows. Endpoint URLs and keys are never returned to the admin UI. Public users never see other subscriptions.
- **FR-059 — Analytics events.** `POST /api/events` must additionally accept `pwa_invite_shown`, `pwa_install`, `pwa_launch` and `notification_open` (with optional `site`, `itemId`, `url`). `pwa_launch` is sent once per 30 min when `display-mode: standalone` (or `navigator.standalone`) is true, using the same `localStorage` dedupe as `site_visit`. Existing analytics dashboards are unchanged (they filter by type); spec 05 exposes the new types generically.

## 6. Design

### 6.1 Data model — migration `0013_pwa.sql`

```sql
-- Generic key/value settings (first consumer: the PWA rollout switch).
CREATE TABLE IF NOT EXISTS app_settings (
  key         TEXT PRIMARY KEY,
  value       JSONB NOT NULL DEFAULT '{}',
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_by  TEXT NOT NULL DEFAULT ''
);

CREATE TABLE IF NOT EXISTS push_subscriptions (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  endpoint         TEXT NOT NULL UNIQUE,
  p256dh           TEXT NOT NULL,
  auth             TEXT NOT NULL,
  expiration_time  TIMESTAMPTZ,
  site_slug        TEXT REFERENCES sites(slug) ON DELETE SET NULL,
  locale           TEXT NOT NULL DEFAULT 'ro',
  channel          TEXT NOT NULL DEFAULT 'all',        -- 'beta' | 'all'
  platform         TEXT NOT NULL DEFAULT 'other',      -- 'ios' | 'android' | 'other'
  standalone       BOOLEAN NOT NULL DEFAULT FALSE,
  fail_count       INTEGER NOT NULL DEFAULT 0,
  last_failed_at   TIMESTAMPTZ,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_seen_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS push_subscriptions_site_idx ON push_subscriptions (site_slug);
CREATE INDEX IF NOT EXISTS push_subscriptions_last_seen_idx ON push_subscriptions (last_seen_at);

CREATE TABLE IF NOT EXISTS push_notifications (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  content_item_id  UUID,                               -- soft reference, like analytics_events.item_id; NULL for kind = 'test'
  status           TEXT NOT NULL DEFAULT 'queued',     -- 'queued' | 'sending' | 'sent' | 'cancelled' | 'failed'
  kind             TEXT NOT NULL DEFAULT 'new_event',  -- 'new_event' | 'test'
  send_after       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  claimed_at       TIMESTAMPTZ,                        -- lease start while status = 'sending'
  attempts         INTEGER NOT NULL DEFAULT 0,         -- claims so far (stale-claim recovery, max 3)
  cancel_reason    TEXT,                               -- 'unpublished' | 'past' | 'no_date' | 'stale' | 'admin'
  title_ro         TEXT NOT NULL DEFAULT '',           -- snapshot for the admin log
  recipients       INTEGER NOT NULL DEFAULT 0,
  sent_count       INTEGER NOT NULL DEFAULT 0,
  failed_count     INTEGER NOT NULL DEFAULT 0,
  triggered_by     TEXT NOT NULL DEFAULT '',           -- admin email or 'mcp'
  created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  sent_at          TIMESTAMPTZ,
  CONSTRAINT push_notifications_item_kind_chk
    CHECK ((kind = 'new_event' AND content_item_id IS NOT NULL) OR (kind = 'test' AND content_item_id IS NULL))
);
-- One notification per event, ever (FR-055). Test sends have no item (content_item_id IS NULL).
CREATE UNIQUE INDEX IF NOT EXISTS push_notifications_item_uidx
  ON push_notifications (content_item_id) WHERE kind = 'new_event';
CREATE INDEX IF NOT EXISTS push_notifications_due_idx ON push_notifications (status, send_after);
```

Status machine: `queued → sending → sent`; `queued → cancelled` (send-time re-validation, stale after a stage-`off` period, or admin cancel); `sending → queued` (stale lease recovered, `attempts` incremented); `sending → failed` after the third stale recovery. A `sending` row older than its 10-minute lease is assumed to belong to a crashed process (single Fastify process, so no other sender exists).

`packages/api/src/db/schema.ts` gets the three matching `pgTable` definitions (`appSettings`, `pushSubscriptions`, `pushNotifications`). `content_item_id` is deliberately not a foreign key (and nullable only for `kind = 'test'`, enforced by the CHECK) so the log survives permanent deletion (the permanent-delete endpoint does *not* purge it — it is an operational log, not item history; see Open questions Q7).

```json
  "push": { "debounceMinutes": 10, "quietHours": { "from": "21:00", "to": "08:00" } } }
```

### 6.6 Server services

`packages/api/src/services/app-settings.ts` — `getSetting<T>(key, defaults)`, `putSetting(key, value, actorEmail)`; 60 s in-memory cache (single process). `getPwaSettings()` wraps it.

`packages/api/src/services/push.ts` (ADR-020):
- `isPushConfigured()` — the three `VAPID_*` env vars are set; `setVapidDetails` once at startup; logs a one-line warning at startup when unset ("push disabled").
- `enqueueNewEventNotification(item, actorEmail)` — called synchronously (awaited, but wrapped in try/catch so it never fails the request) from the three publish paths; applies FR-055 eligibility; computes `send_after = max(now + debounceMinutes, nextAllowedByQuietHours)`; `INSERT … ON CONFLICT DO NOTHING`.
- `startPushWorker()` — `setInterval` every 30 s (guarded against overlap), each tick in this order:
  1. **Stage gate:** read `getPwaSettings().stage`; when `off`, do nothing (rows stay `queued`; nothing is cancelled yet).
  2. **Stale-claim recovery:** `UPDATE push_notifications SET status = CASE WHEN attempts >= 3 THEN 'failed' ELSE 'queued' END, claimed_at = NULL WHERE status = 'sending' AND claimed_at < now() - interval '10 minutes'`. Re-sending a row that was partly delivered before a crash can repeat a notification on a few devices; the per-item `tag`/`topic` makes the repeat replace the earlier one, which is accepted.
  3. **Stale-after-off cancellation:** `UPDATE … SET status = 'cancelled', cancel_reason = 'stale' WHERE status = 'queued' AND send_after < now() - interval '24 hours'` — only rows that sat through a stage-`off` period (or a long outage) can be that old.
  4. **Claim with lease:** `UPDATE push_notifications SET status = 'sending', claimed_at = now(), attempts = attempts + 1 WHERE id IN (SELECT id FROM push_notifications WHERE status = 'queued' AND send_after <= now() ORDER BY send_after LIMIT 5 FOR UPDATE SKIP LOCKED) RETURNING *`.
  5. Per row: re-validate the item through spec 02's `listPublicContent()` / `selectUpcomingEvents()` in `packages/api/src/services/public-content.ts` — that helper returns the **current and upcoming events** (visible items with `data.startDate` that have not ended yet, in-progress multi-day events included); this spec additionally requires `startDate ≥ today` (Europe/Bucharest), because a notice about an event that already started is no longer a "new event" announcement. Cancel with `cancel_reason` `unpublished` (not published / expired / deleted), `no_date` (start date or title removed) or `past` (`startDate < today`). Then select recipients by applying the same visibility rule per subscription `site_slug` (the SQL fragment is the one `public-content.ts` extracts from `routes/content.ts` lines 15–29 — reuse its exported helper rather than copying it); load translations for the distinct locales; build payloads; send with concurrency 20 (small inline semaphore, no new dependency); handle responses (FR-057); update counts, `status='sent'`, `sent_at`, `claimed_at = NULL`.
  Also called once at startup after `runMigrations()` so a restart drains the queue (step 2 then recovers rows the previous process was sending). Only started when `isPushConfigured()`.
- `startSubscriptionSweep()` — daily `setInterval` (and once 5 min after startup) implementing FR-057's inactivity rules.
- `sendTestNotification()` — used by the admin endpoint.
- Text helpers: `buildNotificationText({ item, translation, locale, siteName })` calls `formatEventWhen()` from `packages/shared/src/event-time.ts` (spec 04), reads `location = readLocation({ ...item.data, ...translation?.data })` from `packages/shared/src/event-location.ts` (spec 07) and appends `" · {location}"` to the body when present, and reads `ui_translations` rows for `pwa.push.newEvent.title` ("Eveniment nou · {siteName}") / `pwa.push.newEvent.titleAll` ("Eveniment nou la Betel") with Romanian fallbacks hard-coded only in the API as last resort. "Today" and quiet-hour arithmetic use the Europe/Bucharest helpers from `packages/api/src/services/time.ts` (on `main` since PR #17) — no new timezone code here.
- Hook points: `routes/admin/content.ts` publish handler (line 354 ff., after `logAudit`), `PATCH` handler (line 136 ff., when `state === 'published' && existing.state !== 'published'`), `routes/mcp.ts` `publish_card` (after line 316, `actorEmail = 'mcp'`).

Dependency: `web-push` (^3.6, maintained, Node 24 OK) in `@betel/api`. It is pure JS (no native build), so the esbuild bundle and `dist/package.json` need no change.

### 6.10 Security and privacy

- A push endpoint is a capability URL: never returned by any public endpoint, never written to logs in full (log the push-service host only), shown to admins only as aggregates. Keys (`p256dh`, `auth`) leave the server only inside `web-push` requests.
- Subscriptions hold no identity; `platform`/`standalone`/`locale`/`site_slug` are the only attributes, chosen for targeting and support, not the full user agent. Retention: 180 days of inactivity, immediate deletion on 404/410 or in-app unsubscribe. This is the data-minimisation argument for the GDPR note in `security.md` (§12).
- Permission prompts only from a tap (browser-enforced on iOS and Chromium; the UI never calls `requestPermission()` outside the click handler).
- Public write endpoints are rate-limited (`@fastify/rate-limit`, same pattern as `POST /api/events`): 20/min each. Body size is bounded by validation (endpoint ≤ 2 KB, keys ≤ 256 chars).
- `VAPID_PRIVATE_KEY` is a secret (CapRover env, never in the repo). The public key is public by design.
- Admin endpoints are super-admin only and audited (`pwa.settings.update`, `pwa.invite.campaign`, `pwa.push.test`, `pwa.notification.cancel`).
- Payloads contain only the event title, the "when" text, the optional event location and the hub URL — nothing personal. `navigate` URLs are same-origin only.
- The beta flag is not a security boundary; it is a sampling mechanism. Anyone with the link can opt in, which is acceptable.
- The service worker never caches `/api/push/*` responses (they are POST/DELETE) and never caches `/admin`.

### 6.11 Performance and caching

- The hub's critical path is unchanged: `pwa/` code is small (< 6 KB gz) and the invite/guide components are lazy (`React.lazy`) so visitors who never see them do not download them.
- `GET /api/pwa/config` is one tiny request per 5 min per client, cached 60 s at the HTTP layer and by the SW `NetworkFirst` route; on a Sunday-morning spike it is negligible compared to `/api/content`.
- Splash screens (~30 files) and screenshots are excluded from the precache; iOS fetches exactly one on install.
- Sending N notifications costs N HTTPS requests from the API process with concurrency 20; 2 000 subscriptions ≈ 100 s of background work, off the request path. No queue infrastructure (ADR-010 pattern) — acceptable at this scale; the DB-backed `push_notifications` rows make the work restart-safe.
- The 30 s poller and the daily sweep are the only new periodic work.
