# 02 — RSS feed of upcoming events, AI-agent discoverability

- **Owner area:** feeds, `llms.txt`
- **FR range:** FR-060 – FR-064
- **ADR:** [ADR-021](../../decisions/ADR-021-rss-event-feed.md) (Proposed)
- **Migration:** none
- **Coordination contract:** [README.md](README.md) — this spec obeys it; conflicts are listed under "Contracts" and "Open questions".

## 1. Summary

The hub already knows which content items are events (items with `data.startDate`) and which of them are still current (the Expiration Behavior in `docs/domain/content-model.md`), but that knowledge is only reachable through the React app and the JSON endpoint `GET /api/content`, which returns every published item in display order with no event semantics. An AI agent or feed reader that wants "the upcoming events of Biserica Betel" has to discover an undocumented JSON shape and re-implement the expiry and site-scoping rules.

This spec adds a server-rendered **RSS 2.0 feed of upcoming events** at `/feed.xml` (all sites) and `/:siteSlug/feed.xml` (one site), with machine-parseable event dates in a namespaced extension, optional translation through `?lang=`, conditional-GET caching, and the discoverability hooks that make the feed findable without prior knowledge: `<link rel="alternate">` in the page head, an `/llms.txt` index, and a mention in `robots.txt` (via spec 03). Each item links to the per-item page `/i/:itemId` introduced by spec 03. The outcome: `curl https://<host>/feed.xml` (or any feed reader, or an agent with a fetch tool) yields a chronological digest of upcoming events with stable identifiers, locations, dates and links, kept in sync with the hub by construction because it uses the same selection query.

## 2. Goals / Non-goals

**Goals**

- A valid RSS 2.0 feed of upcoming events, per site and for all sites, generated by the API process (no second deployable).
- Item selection and site scoping identical to the public hub (`GET /api/content`), so the feed never shows an item the hub would hide and vice versa.
- Event dates exposed in a form an agent can parse without reading the description text (ISO 8601 date / date-time with the Bucharest offset).
- Translations through `?lang=<code>` with the same Romanian-fallback semantics as the hub (ADR-014).
- Cheap to poll: ETag + `Cache-Control`, `304 Not Modified`, rate-limited.
- Discoverable: `<link rel="alternate" type="application/rss+xml">` on the hub pages, `/llms.txt`, feed URLs mentioned in `robots.txt`.
- Validates cleanly in the W3C Feed Validator.

**Non-goals**

- Atom or JSON Feed output (see Open question Q1 — designed so a second serializer is a small follow-up).
- Per-item public pages: `/i/:itemId` is owned by spec 03 (README → Fixed contracts); this spec only links to it.
- Hub fragment anchors (`#item-<id>`) and hash scrolling — superseded by `/i/:itemId`; listed as an optional follow-up in Open question Q3.
- Rendering Markdown to HTML in the feed (no new dependency in `packages/api`; description is plain text).
- Feeds of non-event content (announcements without a start date, bookmarked links).
- Push / WebSub notifications to subscribers.
- Analytics of feed consumption (Open question Q6).
- Any change to the content model, the admin UI or the MCP tools.

## 3. Current state

- **Public content query** — `packages/api/src/routes/content.ts` lines 7–113 is the only place that knows the public visibility rules: `state = 'published'` (line 50), `expiresAt` (line 51), the JSONB date filter evaluated against `(NOW() AT TIME ZONE 'Europe/Bucharest')::date` (lines 38–47), the site filter including exclusive items (lines 17–28), display ordering (lines 56–61) and the locale join/merge for non-`ro` locales (lines 64–96). ## 4. User flows

### Flow A — AI agent builds an event digest (crawler / agent)

- Trigger: an agent is asked "what is happening at Biserica Betel next week?" and has a web-fetch tool.
- Steps:
  - the agent fetches `https://<host>/llms.txt` (or the hub page and reads `<link rel="alternate" type="application/rss+xml">`, or `robots.txt`) and learns the feed URLs, one per site plus all-sites
  - it fetches `/feed.xml` (or `/<siteSlug>/feed.xml`), optionally with `?lang=en`
  - it reads items in document order (chronological), using `ev:startdate` / `betel:startDate` / `betel:startTime` for dates, `ev:location` for where, `<link>` (the item page `/i/<id>`, which also carries spec 03's `Event` JSON-LD) to send the human to the item and `betel:actionLink` to the registration / detail page
  - a second fetch with `If-None-Match` gets `304` while nothing changed
- Success state: a correct digest with dates, places and links, with no need to understand `GET /api/content`.
- Failure or edge states: unknown site slug → `404`; unknown or disabled language → `400`; a translated field missing → Romanian text (silent fallback, ADR-014); the agent sorts by `pubDate` instead of event date and gets creation order — mitigated by `ev:startdate` and the chronological document order.

### Flow B — Member subscribes in a feed reader (public visitor)

- Trigger: a member pastes `https://<host>/<siteSlug>` into a feed reader, or taps a reader's "subscribe" action on the hub page.
- Steps:
  - the reader auto-discovers `/<siteSlug>/feed.xml` from `<link rel="alternate">`
  - the reader lists upcoming events; clicking an entry opens the item page `/i/<id>` (spec 03), which shows the item in its site context with a link to the full hub
  - the reader polls at its own cadence; `304` responses keep it cheap
- Success state: the member sees new events in their reader and lands on the right item.
- Failure or edge states: the item expired between the feed fetch and the click → the item page shows spec 03's not-found state (HTTP 404 with `noindex`); a reader that sorts by `pubDate` shows newest-created first — document order is chronological, which most readers also offer.

### Flow C — Admin (no new UI)

- Trigger: an admin publishes a card with a start date.
- Steps: nothing new; within the cache window (≤ 5 minutes, see Design → Caching) the item appears in the feeds of the sites it is scoped to and, unless exclusive, in `/feed.xml`.
- Success state: no admin action is needed for the feed to be correct.
- Failure or edge states: an item without `data.startDate` is not an event and never appears; a poster without `alt` gets a generated title (Design → Item `<title>`), so admins who care about feed titles should fill in `alt`. Spec 04's admin form changes do not interact with this spec.

## 5. Requirements

- **FR-060 — Event feed endpoints.** The API must serve an RSS 2.0 feed of upcoming events at `GET /feed.xml` (all-sites view) and `GET /:siteSlug/feed.xml` (one site), outside the `/api` prefix, with `Content-Type: application/rss+xml; charset=utf-8`. An unknown `siteSlug` returns `404` (`text/plain`). The item set is exactly the items `GET /api/content` (with the same `site` scoping, including exclusive items and the all-sites exclusion of BR-006) would return **that also have a non-empty `data.startDate`**, ordered by `data.startDate` ascending, then `data.startTime` ascending (absent sorts last), then the hub display order. Draft, archived, soft-deleted and expired items (`expiresAt` or JSONB dates, Bucharest calendar day) are never included. The feed is capped at 100 items. **[Planned]**
- **FR-061 — Item content.** Every `<item>` carries: `<title>` (per-type fallback chain, never empty), `<link>` = `absoluteUrl('/i/<id>')` (spec 03's per-item page, identical in both feeds), `<guid isPermaLink="false">urn:uuid:<id></guid>` (stable across sites, languages and edits), `<pubDate>` = `created_at` (RFC 822), `<description>` (plain text: when / where / details lines followed by the item's text), `<category>` = content type, an `<enclosure>` for the item's image when one exists (preview image chain owned by spec 06), `ev:startdate` (and `ev:enddate` when `data.endDate` is set) in W3CDTF, `ev:location` when exactly one site applies, and `betel:startDate`, `betel:startTime`, `betel:endDate`, `betel:site`, `betel:group`, `betel:actionLink` as defined in Design → Feed document. The `startTime` fields and the date-time form of `ev:startdate` are present only when spec 04's `data.startTime` is set. **[Planned]**
- **FR-062 — Language.** `?lang=<code>` selects the language. Omitted → the default locale (`ro`). A code that is not an enabled language returns `400` (`text/plain`). For non-default languages, content fields, group titles and the feed's own UI strings (channel title/description, "when/where/details" labels) use the translation when present and fall back to Romanian per field, exactly like the hub (ADR-014). `<language>` reflects the effective code and `atom:link rel="self"` includes the `lang` parameter when non-default. **[Planned]**
- **FR-063 — Caching, validation, limits.** Responses carry a strong `ETag` (hash of the body), `Cache-Control: public, max-age=300`, and honour `If-None-Match` with `304`. No `Last-Modified` is emitted (the item set changes at Bucharest midnight without any row changing). `HEAD` is supported. The route is rate-limited (120 requests per minute per IP). The output must pass the W3C Feed Validator (`https://validator.w3.org/feed/`) with no errors; recommendations about unknown namespaces are acceptable. All text is XML-escaped and stripped of characters invalid in XML 1.0. **[Planned]**
- **FR-064 — Discoverability.** (a) `packages/app/index.html` carries `<link rel="alternate" type="application/rss+xml" title="…" href="/feed.xml">`; on `/:siteSlug` the per-site feed link is injected server-side through spec 03's head-injection mechanism. (b) `GET /llms.txt` (`text/plain; charset=utf-8`, same caching as the feed) is generated from the `sites` and `languages` tables and lists the hub pages, every feed URL, the `lang` parameter and the public JSON endpoints. (c) spec 03 lists the feed URLs as comments in `robots.txt`; spec 01 adds `/feed.xml`, `/*/feed.xml` and `/llms.txt` to the service-worker `navigateFallbackDenylist` and the matching Vite dev-proxy entries. **[Planned]**

## 6. Design

### 6.1 Format choice

**RSS 2.0** is the primary and only format in v1:

- It is what the product owner asked for and what every aggregator, reader and "fetch URL" tool understands without negotiation.
- RSS 2.0 tolerates namespaced extension elements, which is how event dates are exposed (below).
- The alternatives were weighed in [ADR-021](../../decisions/ADR-021-rss-event-feed.md): **Atom** adds nothing for this audience (same reach, stricter spec, no event vocabulary) and **JSON Feed 1.1** is nicer for agents but would be a second path (`/feed.json`) that the README does not reserve. The serializer is a pure function over a `FeedInput` (6.5), so a JSON Feed serializer is a one-file follow-up if Q1 is answered "yes".

### 6.2 Routes

Both routes live in a new plugin `packages/api/src/routes/feed.ts` (`feedRoutes`) and `/llms.txt` in `packages/api/src/routes/llms-txt.ts` (`llmsTxtRoute`). They are registered in `packages/api/src/index.ts` **right after `shortLinkRedirectRoute` (line 57) and before the SPA `fastifyStatic`** so they are matched before the not-found handler, with no `/api` prefix.

| Route | Query | Response |
|---|---|---|
| `GET /feed.xml` | `lang?` | RSS 2.0, all-sites view |
| `GET /:siteSlug/feed.xml` | `lang?` | RSS 2.0, one site; `404 text/plain` ("Unknown site") when the slug is not in `sites` |
| `GET /llms.txt` | — | `text/plain; charset=utf-8` |

`HEAD` works automatically (Fastify 5 exposes HEAD for GET routes by default); the handler must not rely on `reply.send` side effects that break HEAD. `/admin/feed.xml` resolves to `siteSlug = "admin"`, which is not a site → `404`; this is fine and must not be special-cased.

Rate limit: `{ config: { rateLimit: { max: 120, timeWindow: '1 minute' } } }` on all three routes, same mechanism as `routes/events.ts` line 8.

### 6.3 Item selection — shared public-content service

To guarantee feed/hub parity, the query in `routes/content.ts` is **extracted, unchanged in behaviour**, into `packages/api/src/services/public-content.ts`:

```ts
export interface PublicContentOptions { site: string | null; locale: string }
export interface PublicContentItem { /* row of content_items + groupTitle, data merged with translation */ }
export async function listPublicContent(opts: PublicContentOptions): Promise<PublicContentItem[]>
```

- `routes/content.ts` becomes a thin handler: parse query → `listPublicContent` → `{ site, items }`. Its JSON output must stay byte-for-byte identical (Cypress stubs mirror this shape; the hub depends on `groupTitle`).
- The feed calls `listPublicContent({ site, locale })` and then, in TypeScript (the hub holds tens of items, not thousands):

```ts
export function selectUpcomingEvents(items: PublicContentItem[], limit = 100): PublicContentItem[] {
  return items
    .filter(it => typeof it.data.startDate === 'string' && it.data.startDate.trim() !== '')
    .map((it, i) => ({ it, i }))                       // keep display order as the final tiebreaker
    .sort((a, b) =>
      cmp(a.it.data.startDate, b.it.data.startDate) ||
      cmpTime(a.it.data.startTime, b.it.data.startTime) ||   // absent sorts last (spec 04 field)
      a.i - b.i)
    .map(x => x.it)
    .slice(0, limit)
}
```

Consequences that follow from reusing the hub query (all intentional, none new):

- Multi-day events already in progress (`startDate < today ≤ endDate`) are included and sort first.
- Exclusive items appear only in their site's feed (BR-006). See Q2.
- Group site scope (BR-005) is not applied, exactly as in the hub today (enforcement gap documented in `content-model.md`).
- Legacy `data.date` is ignored; migration `0005_migrate_card_date.sql` promoted it to `startDate`.
- An item with `endDate` but no `startDate` is not an event and is excluded.

Spec 03 (JSON-LD `Event` on the hub pages) needs the same selection; it should consume `listPublicContent` + `selectUpcomingEvents` rather than re-implement them (see Contracts).

### 6.4 Language

- Parameter: `lang` (feed-conventional; matches RSS `<language>`). The internal `locale` name of `GET /api/content` is not exposed as an alias.
- Resolution: `lang` absent → `'ro'` (the hub's `DEFAULT_LOCALE`, the same constant `content.ts` line 9 compares against). Present → must equal the `code` of a row in `languages` with `enabled = true`; otherwise `400`. The default locale row is always enabled (`languages.ts` lines 85–87).
- Content and group titles: `listPublicContent` already merges `content_translations.data` and `group_translations.title` for non-default locales (`content.ts` lines 64–96).
- Feed UI strings: a tiny module `packages/api/src/services/feed-strings.ts` holds the keys and Romanian defaults and, for a non-default `lang`, reads `ui_translations` for those keys in one query and falls back per key — the server-side twin of `t(key, fallback)` in `LanguageContext.tsx` lines 89–96:

| Key | Romanian default | Used for |
|---|---|---|
| `feed.title` | `Evenimente — Betel Info` | all-sites channel title |
| `feed.title.site` | `Evenimente — Betel {siteName}` | per-site channel title |
| `feed.description` | `Evenimentele următoare ale bisericii Betel` | all-sites channel description |
| `feed.description.site` | `Evenimentele următoare — Betel {siteName}` | per-site channel description |
| `feed.when` | `Când` | description label |
| `feed.where` | `Unde` | description label |
| `feed.details` | `Detalii` | description label |
| `feed.untitled` | `Eveniment` | title fallback prefix |

The same keys and defaults are added to `packages/app/src/public/i18n/keys.ts` (`UI_KEYS.FEED_*`) and to `KNOWN_KEYS` in `TranslationsPage.tsx`, so super-admins see them on the Translations page and "generate" produces them with AI. (`{siteName}` interpolation mirrors the `vars` mechanism of `t()`.) Spec 04's "when" formatter may add its own keys to `keys.ts`; both specs append keys and the coordinator merges — no key names overlap (04 is asked to avoid the `feed.` prefix).

The "when" text itself (e.g. `vineri, 14 noiembrie 2026, 18:00`) is produced by **spec 04's shared formatter**, called with `(startDate, endDate, startTime, lang)`; this spec does not format dates.

### 6.5 Feed document

Serializer: `packages/api/src/services/rss.ts`, a pure function `buildEventFeed(input: FeedInput): string` with no DB or Fastify imports, so it can be unit-tested. `FeedInput` is built by the route from: the channel (site or null, base URL, lang, strings, generator version), the selected items, the site rows (for names/addresses), the image lengths (one query on `media` by URL, 6.5.1), and the when-text per item (spec 04).

Namespaces declared on `<rss>`:

| Prefix | URI | Why |
|---|---|---|
| `atom` | `http://www.w3.org/2005/Atom` | `atom:link rel="self"`, the validator's recommended self-reference |
| `ev` | `http://purl.org/rss/1.0/modules/event/` | the long-standing RSS "mod_event" vocabulary (`startdate`, `enddate`, `location`); agents and some readers already know it |
| `betel` | `urn:betel:feed:1.0` | raw, lossless event fields and hub-specific data (site, group, action link). A URN, so it does not vary with `PUBLIC_BASE_URL` |

Channel:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<rss version="2.0"
     xmlns:atom="http://www.w3.org/2005/Atom"
     xmlns:ev="http://purl.org/rss/1.0/modules/event/"
     xmlns:betel="urn:betel:feed:1.0">
  <channel>
    <title>Evenimente — Betel Example Site</title>
    <link>https://info.bisericabetel.com/example-site</link>
    <description>Evenimentele următoare — Betel Example Site</description>
    <language>ro</language>
    <lastBuildDate>Tue, 27 Oct 2026 18:40:11 GMT</lastBuildDate>
    <generator>Betel Info 1.12.0</generator>
    <ttl>60</ttl>
    <image>
      <url>https://info.bisericabetel.com/icons/icon-512.png</url>
      <title>Evenimente — Betel Example Site</title>
      <link>https://info.bisericabetel.com/example-site</link>
    </image>
    <atom:link rel="self" type="application/rss+xml"
               href="https://info.bisericabetel.com/example-site/feed.xml"/>
    <!-- items… -->
  </channel>
</rss>
```

(`example-site` / "Example Site" are placeholders — site slugs and names come from the `sites` table at request time; the host comes from `absoluteUrl`.)

- `<title>` / `<description>`: `feed.title` / `feed.description` (all sites) or the `.site` variants with the site's `name`.
- `<link>`: `absoluteUrl('/')` or `absoluteUrl('/<slug>')`.
- `<language>`: the effective `lang` (RSS wants an RFC 1766 code; `languages.code` values such as `ro`, `en` qualify).
- `<lastBuildDate>`: `max(updated_at)` of the included items, or the request time when the feed is empty.
- `<generator>`: `Betel Info <rootPkg.version>`.
- `<ttl>60` (minutes) — a hint for readers, consistent with the HTTP cache window.
- `<atom:link rel="self">`: the absolute feed URL including `?lang=` when non-default.
- An empty feed is a valid feed with zero `<item>`s (not a 404).

Item:

```xml
<item>
  <title>Seară de tineret</title>
  <link>https://info.bisericabetel.com/i/3f2c8c8e-…</link>
  <guid isPermaLink="false">urn:uuid:3f2c8c8e-…</guid>
  <pubDate>Tue, 20 Oct 2026 09:12:00 GMT</pubDate>
  <category>card</category>
  <description>Când: vineri, 14 noiembrie 2026, 18:00
Unde: Example Site — Str. Exemplu 1, Cluj-Napoca
Detalii: https://forms.example/inscriere

Seară de laudă și părtășie pentru tineri. Intrarea este liberă.</description>
  <enclosure url="https://info.bisericabetel.com/uploads/9a1b….webp" length="183422" type="image/webp"/>
  <ev:startdate>2026-11-14T18:00:00+02:00</ev:startdate>
  <ev:location>Example Site — Str. Exemplu 1, Cluj-Napoca</ev:location>
  <betel:startDate>2026-11-14</betel:startDate>
  <betel:startTime>18:00</betel:startTime>
  <betel:site slug="example-site">Example Site</betel:site>
  <betel:group>Tineret</betel:group>
  <betel:actionLink>https://forms.example/inscriere</betel:actionLink>
</item>
```

Field rules:

| Element | Rule |
|---|---|
| `<title>` | Card: `data.title`. Richtext: `data.title`, else the first non-empty line of `data.body` with leading `#`, `*`, `_`, `>` and surrounding whitespace stripped, truncated to 80 characters. Video: `data.title`. Poster: `data.alt`. **Final fallback for every type:** `"<feed.untitled> — <when text>"` (e.g. `Eveniment — 14 noiembrie 2026`), so a title is never empty. `data.name` (poster, admin-only) is never used. |
| `<link>` | `absoluteUrl('/i/<id>')` — spec 03's per-item page (README → Fixed contracts), the same URL in `/feed.xml` and every site feed. Always present, same-origin, stable; the page shows the item in its site context, carries the `Event` JSON-LD and links to the hub. Q3 lists the rejected alternatives. |
| `<guid>` | `urn:uuid:<content_items.id>`, `isPermaLink="false"`. Identical across sites and languages; a duplicate (BR-009) is a new item with a new guid, which is correct. |
| `<pubDate>` | `created_at` in RFC 822 (`toUTCString()`). Not `updated_at`: reorders bump `updated_at` (`routes/admin/content.ts` lines 310–337), which would make every item look "new" after a drag-and-drop. Q4. |
| `<category>` | the content type (`card`, `poster`, `richtext`, `video`). |
| `<description>` | Plain text, XML-escaped, lines joined with `\n`: `"<feed.when>: <when text>"`; `"<feed.where>: <location>"` if a location exists; `"<feed.details>: <actionLink>"` if a link exists; blank line; then the item text — card `data.description`, richtext `data.body`, video `data.url`, poster nothing. Markdown is left as authored (no HTML rendering; see Non-goals). |
| `<enclosure>` | The item's image per spec 06's preview-image chain (Card → `data.thumbnail`, Poster → `data.imageUrl`, locale overrides already merged by `listPublicContent`). `url` is made absolute with `absoluteUrl` when relative (`/uploads/…`). `length` = `media.size` for the matching `media.url` row, else `0` (external URLs accepted by MCP, ADR-015). `type` = `media.mime_type`, else inferred from the extension, else `image/*` → use `application/octet-stream`. Omitted when the item has no image. |
| `ev:startdate` | W3CDTF. With `data.startTime` (spec 04): the ISO 8601 date-time with the Bucharest offset from 04's builder (`2026-11-14T18:00:00+02:00`). Without: the bare date `2026-11-14`. |
| `ev:enddate` | Present only when `data.endDate` is set: bare date. |
| `ev:location` | Present when exactly one site applies: the site feed's site, or (in `/feed.xml`) an item with `exclusive_site` or `sites.length === 1`. Value: `"<name> — <address>"` or `"<name>"` when `address` is null. Omitted for church-wide items in the all-sites feed and when `sites.length > 1`. |
| `betel:startDate`, `betel:endDate` | The raw `YYYY-MM-DD` strings. |
| `betel:startTime` | The raw `HH:mm` when set (spec 04). Absent means all day / time unknown (README contract). |
| `betel:site` | One element per applicable site (`exclusive_site`, else each of `sites[]`, else the feed's site, else none), `slug` attribute + `name` text. |
| `betel:group` | The (translated) `groupTitle` when the item is grouped. |
| `betel:actionLink` | The resolved link per the Link Resolution Rule (`content-model.md`): site feed → `data.siteLinks[siteSlug] || data.link`; all-sites feed → `data.link`. Absent when neither exists. Short links are not used here (they are channel-tracking links owned by spec 06, not the item's canonical destination). |

Escaping: one `escapeXml()` helper handles `& < > " '` and removes code points not allowed in XML 1.0 (`[^\x09\x0A\x0D\x20-퟿-�\u{10000}-\u{10FFFF}]`). CDATA is not used.

#### 6.5.1 Image length lookup

One query per request: `SELECT url, size, mime_type FROM media WHERE url = ANY($1)` for the distinct relative image URLs of the selected items. External URLs skip the lookup.

### 6.6 Caching

Consistent with ADR-013's principle (entry points revalidate; stable things cache) but a different category: a **dynamic, public, cheap-to-regenerate document**.

- `ETag: "<sha1 of body, hex>"` (strong; the body is deterministic for a given DB state and `now`).
- `Cache-Control: public, max-age=300` — readers and CapRover's nginx may reuse for 5 minutes; publishing an event is visible within that window. Not `no-cache`: the point is to make polling cheap.
- `If-None-Match` matching → `304` with the same `ETag` and `Cache-Control`, empty body.
- **No `Last-Modified` / `If-Modified-Since`:** the set of upcoming events changes at Bucharest midnight (expiry) without any row's `updated_at` changing, so a modification date cannot be computed honestly. The ETag covers this because the body changes.
- The ETag must be computed over the final body, after the `lang` resolution, so `/feed.xml` and `/feed.xml?lang=en` never share an ETag.
- `/llms.txt` uses the same `ETag` + `Cache-Control`.
- No in-process memoisation in v1: the query is the same one the hub runs on every page load (NFR-005 already sizes it) and feed traffic is a small fraction of hub traffic. If feed polling ever matters, add a 60 s in-memory cache keyed by `(site, lang)` inside the route — the serializer stays pure.
- The service worker never sees these paths (navigation denylist, spec 01) and its `/api/` runtime cache is unaffected.

### 6.7 Discoverability

- **Static head tag** (`packages/app/index.html`, owned by this spec): `<link rel="alternate" type="application/rss+xml" title="Evenimente — Betel Info" href="/feed.xml" />`. Relative `href` is valid in HTML; readers resolve against the page URL. The `title` attribute is a hard-coded Romanian string in an HTML file that has no `t()`; it mirrors `feed.title`'s default and is the same compromise as `<title>Betel Info</title>` on line 15.
- **Per-site head tag** on `/:siteSlug`: spec 03's server-side injection adds `<link rel="alternate" type="application/rss+xml" title="Evenimente — Betel <name>" href="/<slug>/feed.xml">` **in addition to** the static all-sites tag. This spec provides the markup; 03 renders it (README → Ownership table, "Static `<head>` tags").
- **`/llms.txt`** (this spec): generated per request from `sites` (ordered by slug, like `GET /api/sites`) and enabled `languages`, following the llms.txt convention (H1, blockquote summary, H2 sections of `- [name](url): description` lines). English text (it targets agents; the project's documentation language). Structure:

```markdown
# Betel Info

> Information hub of Biserica Betel, a multi-site church: upcoming events, announcements and useful links, filtered per site (location). Content is authored in Romanian; translations may exist for the languages listed below.

Dates are calendar dates in Europe/Bucharest; `startTime`, when present, is local wall-clock time.

## Upcoming events (RSS 2.0)

- [All sites](https://<host>/feed.xml): every upcoming event that is not exclusive to a single site
- [<Site name>](https://<host>/<slug>/feed.xml): upcoming events for <Site name>
  (one line per site)

Add `?lang=<code>` for a translation; available codes: ro (default), en, …
Items carry `ev:startdate`, `ev:enddate`, `ev:location` and `betel:*` elements with ISO 8601 dates.

## Hub pages

- [All sites](https://<host>/)
- [<Site name>](https://<host>/<slug>)
  (one line per site)

## Public JSON API

- [Sites](https://<host>/api/sites): `{ sites: [{ slug, name, accent }] }`
- [Content](https://<host>/api/content?site=<slug>&locale=<code>): published, non-expired items in display order; `data.startDate` / `data.endDate` mark events
- [Languages](https://<host>/api/languages): enabled languages
```

- **`robots.txt`**: spec 03 adds `# Event feeds: /feed.xml, /<siteSlug>/feed.xml (see /llms.txt)` as comments (README: comments only).
- **Item pages**: every feed `<link>` targets `/i/<id>` (spec 03, FR-069). No hub DOM change is needed by this spec.

### 6.8 Configuration

No new environment variables. Every absolute URL comes from spec 03's `absoluteUrl(path)` (`packages/api/src/services/public-url.ts`), which always returns an absolute URL: production refuses to start without `PUBLIC_BASE_URL`, development defaults to `http://localhost:3100` (03 → FR-066). The feed never builds URLs by hand.

### 6.9 Security and privacy

- Public, unauthenticated, read-only; only `published`, non-expired, non-deleted items are selected — the same gate as the hub, enforced by the shared service, so drafts can never leak through the feed.
- Output is XML-escaped; admin-authored text cannot inject markup. No HTML in the feed at all.
- No personal data: items, sites and group titles only. Nothing about the requester is stored (see 6.10).
- `lang` is validated against `languages`; `siteSlug` against `sites`; both are used only as Drizzle parameters.
- Rate-limited per IP (120/min); `304` responses are cheap. A 100-item cap bounds the body size.
- `/llms.txt` discloses only URLs that are already public.

### 6.10 Analytics

**Not tracked in v1.** Reasons: readers poll every few minutes, so per-fetch rows would dwarf real visits and would need an IP-keyed dedup map like the short-link one (`routes/short-links.ts` lines 9–17); `event_type` is restricted to `site_visit` / `link_click` in the ingest route and dashboard; and the value of the number is low. Fastify's request log (`logger: true`, `index.ts` line 43) already records every `/feed.xml` hit for ad-hoc counting. If tracking is wanted later it is a new `event_type` (`feed_fetch`) emitted by this spec's route, which spec 05 exposes generically (README → Ownership). Q6.

Clicks from the feed land on `/i/<id>`; whether and how item-page views are tracked is spec 03's call (its `track()` changes in T6). Nothing feed-specific is recorded.

## 8. Rollout

- No feature flag: the routes are harmless when unused and have no admin surface.
- No migration.
- Deploy order: spec 03's T1 (`public-url.ts`) must be in `main` before this spec's T4/T5 merge (03 marks it "merge first"). Spec 03's `/i/:itemId` (its T4 + T6) should be deployed before, or together with, this spec's T4: until it exists a feed `<link>` opens the SPA shell at `/i/<id>`, which renders nothing — acceptable for a few days of staging, not for production. Spec 04 may merge before or after; the feed degrades to date-only until 04's formatter exists. Spec 01's denylist entry should ship in the same release or earlier, otherwise an installed PWA navigating to `/feed.xml` from within the app gets the SPA shell (direct fetches by readers and agents are unaffected since they never run the service worker).
- Production prerequisite: `PUBLIC_BASE_URL` set in CapRover (03). Verify with `curl -sI https://<host>/feed.xml`.
- Rollback: revert the commit(s); no data changes. Readers that cached the feed will see `404`/SPA HTML on the next poll and simply report an error.

## 9. Testing

The Cypress suite stubs the API, so the feed body cannot be tested there. Split:

**Unit (new, `node --test`, no new dependency)** — `packages/api/src/services/rss.test.ts` and `public-content.test.ts` (the pure `selectUpcomingEvents`), run with `node --import tsx --test src/**/*.test.ts` via a new `test:unit` script in `packages/api/package.json` (Q7):

- builds a feed from a fixture `FeedInput` and asserts: well-formed XML (parse with a minimal check: balanced, declaration present), channel fields, `atom:link` self URL with/without `lang`, item count cap, chronological order with `startTime` tiebreak and display-order tiebreak, title fallback chain for each type, `ev:startdate` date vs date-time, `ev:location` present/absent rules, `betel:site` multiplicity, `betel:actionLink` site override vs default, enclosure `length` fallback `0`, XML escaping of `&<>"'` and removal of a `\u0000`, empty feed produces zero items and a valid document.

**Cypress (`cypress/e2e/feed-discovery.cy.ts`)**

- Happy flow: visit `/` with stubbed sites/content; assert `head link[rel="alternate"][type="application/rss+xml"]` has `href="/feed.xml"`.
- Regression: the alternate link is still present on `/<slug>` (the static tag must not be removed by 03's injection, which adds the per-site one next to it; the per-site tag itself is server-rendered and is covered by 03's `seo-head.cy.ts`).
- The feed → item-page journey (`/i/:id` renders the item, not-found state for an expired item) is covered by spec 03's `item-page.cy.ts`; no duplicate here.

**Manual (backend behaviour, must be reported in the PR)**

1. `pnpm dev:api` with seed data; `curl -s localhost:3100/feed.xml | xmllint --noout -` → no errors.
2. Paste the production URL into `https://validator.w3.org/feed/` → "Valid RSS" (namespace recommendations acceptable).
3. `curl -sI localhost:3100/feed.xml` → `200`, `Content-Type: application/rss+xml; charset=utf-8`, `ETag`, `Cache-Control: public, max-age=300`, no `Last-Modified`.
4. Repeat with `-H 'If-None-Match: <etag>'` → `304`.
5. `/<existing-slug>/feed.xml` → 200 with only that site's items (incl. an exclusive item); `/nope/feed.xml` → 404; `/feed.xml` omits the exclusive item.
6. `?lang=en` on an item with an English translation → translated title; `?lang=xx` → 400; a disabled language → 400.
7. Create a draft card with a start date → absent; publish → present within 5 minutes (or immediately with a fresh `curl`); set its end date to yesterday → absent.
8. An item with `startDate` in the past and `endDate` in the future → present and first.
9. Hit the route 130 times in a minute → `429` after 120.
10. `curl -s localhost:3100/llms.txt` lists every site from `GET /api/sites` and the enabled languages.
11. Subscribe in one desktop reader (e.g. NetNewsWire) and one web reader (e.g. Feedly): items show, clicking opens `/i/<id>` with the item rendered (requires 03's item page to be deployed).
12. `HEAD /feed.xml` returns headers only.
