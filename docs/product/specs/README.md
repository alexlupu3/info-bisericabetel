# Feature Specs — Coordination

Implementation-ready specs for the next batch of features, written so that each one can be handed to a different developer and built in parallel. This file is the **contract between the specs**: ownership of shared concerns, reserved IDs and the interfaces one spec provides to another. When a spec and this file disagree, this file wins until it is amended.

Specs live in this folder until they are implemented. Each spec proposes its edits to the shared docs (requirements, domain, architecture, ADR index) in its own "Doc integration" section; those edits are applied in one pass by the coordinator, never by the individual specs, so that parallel work never touches the same file.

## Fixed contracts

- **Absolute URLs:** `PUBLIC_BASE_URL` (e.g. `https://info.bisericabetel.com`, no trailing slash). Defined and documented by 3; required in production for 2, 3, 5, 6. Production refuses to start without it; in development it defaults to `http://localhost:3100` with a startup warning (FR-066 in `docs/product/requirements.md`; shipped in `packages/api/src/services/public-url.ts`), so `absoluteUrl()` always returns an absolute URL.
- **Event time:** `data.startTime` as above. Absent means "all day / time unknown"; consumers must render date-only in that case. Helpers in `packages/shared/src/event-time.ts` (shipped): `CHURCH_TIME_ZONE`, `EventSchedule`, `CLOCK_TIME_PATTERN`, `isClockTime`, `isSingleDayEvent`, `invalidStartTime`, `eventStartInstant`, `eventStartIso`, `utcOffsetAt`, `FormatEventWhenOptions`, `formatEventWhen`, `formatEventTime`, `eventSortKey`, `compareEventSchedules`. Fixed validation errors (checked in this order): `startTime must be a 24-hour clock time in HH:mm format`; `startTime requires startDate`; `startTime is only allowed for single-day events (no endDate, or endDate equal to startDate)`. Rules: BR-035, `content-model.md` → Event start time.
- **Event location:** `data.location` as above (Cards only, ≤ 70 characters, translated value with Romanian fallback). Absent means "no explicit location"; consumers then fall back to their current behaviour (e.g. the site as the place). When present it takes precedence over the site as the human-readable place name. Helpers in `packages/shared/src/event-location.ts` (shipped: `LOCATION_MAX_LENGTH = 70`, `LOCATION_SOFT_LENGTH = 50`, `normalizeLocationText`, `invalidLocation`, `readLocation`); length is measured in UTF-16 code units after normalisation. Write rule (`applyLocation()` in `packages/api/src/services/event-location.ts`, shared by REST, remote MCP and translation PUT; the AI job uses `sanitizeTranslatedLocation()`): stored values are non-empty, 1–70 code units; empty input removes the key; validated on the resulting type and data of every write. Fixed error strings (checked in this order): `location must be a string`; `location must be at most 70 characters`; `location is only supported on cards`. Admin copy is "Loc de desfășurare" — never "Locație", which already means a church site.
- **Feed URLs:** `/feed.xml` (all sites) and `/:siteSlug/feed.xml` (one site). 2 may add query parameters (e.g. language) but not change these paths.
- **Preview image of a content item:** 6 owns two separate things. (a) **Field selection** — Card → `data.thumbnail`, Poster → `data.imageUrl`, locale override before the base image (`content-model.md`); every spec that shows an item's picture uses this choice. (b) **The share-image service** `packages/api/src/services/preview-image.ts` — the full chain of FR-086 (item images → site brand → hub brand) served as 1200×630 JPEG derivatives under `/uploads/og/`. 3 uses (b) for `og:image` on item pages. 2 uses only (a) and intentionally never calls (b): RSS enclosures must state a true `length`/`type`, so they link the original upload and its `media` row (FR-061, ADR-021). 3's JSON-LD `Event.image` uses (a), with the organisation logo as its own last fallback (03 §6.2).
- **Shipped by 3 (2026-10-28):** `absoluteUrl()` / `publicBaseUrl()` (`packages/api/src/services/public-url.ts`); `registerHeadTags(fn: (page: PageModel) => string[])` (`packages/api/src/services/seo/head-tags.ts`) for extra `<head>` tags on server-rendered pages (2's per-site RSS `<link rel="alternate">`); `listPublicContent`, `findPublicItem` and `selectUpcomingEvents` in `packages/api/src/services/public-content.ts` (extracted by 3, owned by 2); the `GET /api/content/:id` endpoint; `pageTitle()`, `itemWhen()`, `itemSiteSlug()` and the other SEO text helpers in `packages/shared/src/seo.ts`; Romanian UI defaults in `packages/shared/src/i18n-defaults.ts` (`UI_DEFAULTS`). `packages/shared/src/event-location.ts` held a `readLocation()` stub until 7 shipped. 3 also added `/robots.txt` and `/sitemap.xml` to the Vite `server.proxy` and the service-worker `navigateFallbackDenylist` (1 still owns the rest of those lists).
- **Shipped by 2 (2026-10-29):** `GET /feed.xml`, `GET /:siteSlug/feed.xml` (`?lang=`) and `GET /llms.txt` (`packages/api/src/routes/feed.ts`, `routes/llms-txt.ts`); the pure serializer `buildEventFeed()` (`services/rss.ts`) and `feed.*` UI keys (`UI_DEFAULTS`, `services/feed-strings.ts`); the static all-sites `<link rel="alternate" type="application/rss+xml">` in `packages/app/index.html` and the per-site one through `registerHeadTags()`. - **Shipped by 5 (2026-10-29):** the MCP tool contract `packages/shared/src/mcp-tools.ts` (entry `@betel/shared/mcp-tools`: `toolContract`, `toolNames`, `ToolHandlers`, `clockTimeSchema`, `dateRangeShape`), already holding 4's `startTime`; both servers register every tool from it, so 7's `location` and 6's `previewMode` are added there once (plus their handlers — a missing handler fails `pnpm lint`). `services/short-links.ts` (`createShortLink`, `listShortLinks`, `deleteShortLink`, `shortLinkUrl`) under the admin handlers in `routes/admin/short-links.ts`; `routes/short-links.ts` now holds only `/s/:code` and the exported `resolveUrl()` (BR-012). - **Per-item pages:** `/i/:itemId` is a public SPA route owned by 3 (Google `Event` rich results need one URL per event). It is **not** added to the service-worker denylist: server-rendered HTML (ADR-022) serves first loads, crawlers and clients without a service worker, while navigations controlled by the service worker get the precached shell for `/`, `/:siteSlug` and `/i/:itemId` alike and the SPA fetches the data. Only server-only routes are denylisted.
- **`noindex` policy** is owned by 3; 6 applies `X-Robots-Tag: noindex` inside `/s/:code`.
- **Sites are data** — no spec hard-codes site slugs, names, cities or accent colours (see `AGENTS.md`).

## Integration of shared docs

Applied now (on the specs branch): the planned FRs in `docs/product/requirements.md` → "Planned Features", the roadmap entry, and the ADR index rows (status Proposed).

Applied **with the code**, by the implementing developer: every other "Doc integration" snippet (domain rules, BR entries, entities, configuration, security, overview, deployment, user flows, amendments to existing FRs). Those docs describe the as-built system, so they change only when the behaviour does. When a feature ships, move its FRs out of "Planned Features" into the permanent section, set its ADRs to Accepted, and delete the spec (git history keeps it).

## Spec template

Every spec uses these sections, in this order:

1. **Summary** — the problem and the outcome, in a few sentences.
2. **Goals / Non-goals**
3. **Current state** — what exists today, with file references.
4. **User flows** — public visitor, admin, and (where relevant) crawler / AI agent.
5. **Requirements** — numbered with the reserved FR IDs, each testable.
6. **Design** — data model, API, UI, configuration (new env vars), security and privacy, performance and caching.
7. **Contracts** — what this spec provides to and consumes from others (must match the tables above).
8. **Rollout** — flags, migration, deploy order, rollback.
9. **Testing** — Cypress happy flow and regression scenarios, plus the manual checks for backend behaviour the suite does not cover.
10. **Work breakdown** — tasks sized for one developer each, with the files each task touches and their dependencies.
11. **Open questions** — decisions the product owner must make, each with a recommended default.
12. **Doc integration** — the exact additions this spec proposes for shared docs (`requirements.md`, `content-model.md`, `business-rules.md`, `configuration.md`, `security.md`, `roadmap.md`, `user-flows.md`, ADR index). Written as ready-to-paste snippets; not applied by the spec author.
