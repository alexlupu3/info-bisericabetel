# ADR-019: Custom service worker via `injectManifest`

- **Status:** Proposed
- **Date:** 2026-10-28
- **Related:** ADR-013 (HTTP cache strategy, `autoUpdate`), ADR-020 (Web Push and staged rollout)
- **Implements:** FR-050, FR-051

## Context

The public hub's service worker is generated by Workbox's `generateSW` strategy through `vite-plugin-pwa` (`packages/app/vite.config.ts`). That strategy produces the whole worker from configuration: precache manifest, navigation fallback with a denylist, and runtime caching rules. It cannot host application code, and Web Push (spec 01, FR-054–FR-057) needs three handlers inside the worker — `push`, `notificationclick` and `pushsubscriptionchange`.

Two other forces apply:
- ADR-013 chose `registerType: 'autoUpdate'` so that every visitor runs the latest build within one page load after a deploy. Whatever replaces the generated worker must keep that behaviour (`skipWaiting` + `clientsClaim`, entry files served `no-cache`).
- Specs 02, 03 and 06 add server-rendered paths (`/robots.txt`, `/sitemap.xml`, `/feed.xml`, `/:siteSlug/feed.xml`, `/llms.txt`, `/s/*`) that must never be answered by the SPA shell, while spec 03's `/i/:itemId` is a hub page like `/` and `/:siteSlug`: server-rendered on first load and for crawlers (ADR-022), shell-served by the service worker on in-app navigations. The denylist therefore becomes a maintained, shared artefact rather than an inline regex list.

## Options Considered

### Option A — keep `generateSW` and add `workbox.importScripts: ['push-sw.js']`
A plain JavaScript file in `public/` is imported by the generated worker and holds the push handlers.
- Pros: smallest diff; configuration-driven precache and routing stay as they are.
- Cons: the push code is untyped JavaScript outside the TypeScript toolchain; imported scripts are versioned separately from the worker and need their own `no-cache` rule; two places define worker behaviour; `pushsubscriptionchange` needs access to configuration that is awkward to pass into an imported script.

### Option B — `injectManifest` with a TypeScript worker `src/sw.ts` (chosen)
The worker is application code: Workbox modules are imported, the precache manifest is injected at build time, and all routing, caching and push logic live in one typed file.
- Pros: one file, type-checked (`tsconfig.sw.json`, `lib: WebWorker`), testable constants (the denylist is an exported module), the same `autoUpdate` semantics expressed explicitly, standard vite-plugin-pwa setup with documentation and examples.
- Cons: the precache/routing configuration moves from `vite.config.ts` into code, so a developer must replicate the existing `NetworkFirst` rule and the navigation denylist (easy to forget without this ADR); a second `tsc` pass in `pnpm lint`.

### Option C — Safari Declarative Web Push only, no custom worker
Safari 18.4+/iOS 18.4+ can display a `"web_push": 8030` JSON payload without a service worker.
- Pros: no worker changes.
- Cons: Chromium and Firefox (every Android member) still require a `push` handler; Declarative Web Push is a Safari-only optimisation. Rejected as the sole mechanism, but the payload format is adopted as a superset (see ADR-020).

## Decision

Use `strategies: 'injectManifest'` with `packages/app/src/sw.ts` as the worker source and keep `registerType: 'autoUpdate'`.

Rules that follow:
1. `sw.ts` must call `precacheAndRoute(self.__WB_MANIFEST)`, `cleanupOutdatedCaches()`, `self.skipWaiting()` and `clientsClaim()` — this is ADR-013's update behaviour, now explicit.
2. Navigation requests are served from the precached `index.html` through a `NavigationRoute` whose denylist is the exported constant in `packages/app/src/pwa/denylist.ts`. The list contains `/admin*`, `/s/*`, `/api/*`, `/uploads/*`, `/mcp*`, `/health`, `/robots.txt`, `/sitemap.xml`, `/feed.xml`, `/*/feed.xml`, `/llms.txt`. The per-item SPA route `/i/:itemId` is part of the shell and is never denylisted. Server-rendered HTML (ADR-022) serves first loads, crawlers and non-SW clients; navigations controlled by the service worker get the precached shell for `/`, `/:siteSlug` and `/i/:itemId` alike, and the SPA fetches data. Only server-only routes (`/s/*`, `/robots.txt`, `/sitemap.xml`, `/feed.xml`, `/*/feed.xml`, `/llms.txt`, `/uploads/*`) are denylisted. A spec that adds a server-only path declares it in its own spec; the PWA owner (spec 01) adds it to the shared denylist and to the Vite `server.proxy` for development in the same change.
3. Runtime caching keeps the existing `NetworkFirst` (5 min) rule for same-origin `GET /api/*` and adds `CacheFirst` (30 days, 60 entries) for `/uploads/*` images.
4. Splash screens and manifest screenshots (`public/splash/**`, `public/screenshots/**`) are excluded from the precache (`injectManifest.globIgnores`); they are large and used once by the OS.
5. The worker is type-checked by `tsconfig.sw.json` (`lib: ["ES2022", "WebWorker"]`), excluded from the app's `tsconfig.json`, and `pnpm lint` runs both.
6. Registration stays automatic (`registerSW.js` injected by the plugin); the hand-written `<link rel="manifest">` in `index.html` is removed because the plugin injects one (the built page currently has two).
7. The file names (`sw.js`, `registerSW.js`, `workbox-*.js`, `manifest.webmanifest`) do not change, so the `no-cache` rules in `packages/api/src/index.ts` keep applying.

## Implementation

- `packages/app/vite.config.ts`: `strategies`, `srcDir: 'src'`, `filename: 'sw.ts'`, `injectManifest.globPatterns/globIgnores`, `manifest`, `pwaAssets`, `server.proxy` entries.
- `packages/app/src/sw.ts`, `packages/app/src/pwa/denylist.ts`, `packages/app/tsconfig.sw.json`, `packages/app/package.json` (`lint`, workbox dev dependencies).
- Push handlers: see ADR-020 and `docs/product/specs/01-pwa.md` §6.3.

## Consequences

- Easier: push notifications, future worker features (badging, background sync), unit-testable routing constants, one place to read when debugging "why did the SW answer this URL".
- Harder: configuration drift — a change to caching rules now happens in code; reviewers must check `sw.ts` when server routes are added. The denylist constant and the manual check "server routes are not answered by the SW" in spec 01 mitigate this.
- Risk: a broken `sw.ts` ships a broken worker to every visitor on the next load. Mitigation: `pnpm lint` type-checks it; the production build is smoke-tested (`node packages/api/dist/index.js`) before deploy; `autoUpdate` means a fixed build replaces it within one page load.
