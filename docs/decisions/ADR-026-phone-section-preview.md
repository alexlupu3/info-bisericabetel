# ADR-026: Phone-only collapsed group preview (swipeable tile deck) with CSS geometry and a pin column

- **Status:** Accepted
- **Date:** 2026-11-04
- **Related:** ADR-022 (server-rendered snapshot and parity), ADR-013 (HTTP cache)
- **Implements:** FR-096 – FR-104, FR-115
- **Revised:** 2026-11-05 — user testing replaced the fanned hand of 3 tiles with a two-tile swipeable deck and added a per-group opt-out; 2026-11-06 — swipe reworked into two piles where only one card moves (see Revision)

## Context
Long groups make the phone feed long: nine events stack into several screens before the next group. The public hub is also server-rendered (ADR-022): the snapshot must show the same items as the SPA, and crawlers must keep seeing every item. Editors want to choose which items lead a shortened group without changing the group's (often chronological) order.

## Options Considered
- **Capped list + "see all"** (first 3 in the grid, a counted row expands in place): cheapest and calmest, but plain; its mechanics are kept underneath the chosen option.
- **Fanned "hand of cards"** (3 trimmed tiles fanned like cards held in a hand, dealt into the grid on demand): the most compact, but the tiles had to be clipped and re-styled (date cover, hidden description and CTA), and testers found a fan of three hard to read. Chosen at first; revised into a two-tile swipeable deck (see Revision).
- **Horizontal snap carousel**: shortest section, but items past the second hide behind a swipe that desktop users rarely try and that conflicts with the iOS back-swipe.
- **Where to apply it**: everywhere vs. phones only. On desktop three items already fill one grid row, so collapsing saves little; phones only.
- **How to collapse**: remove items from the DOM on the client (layout shift on hydration, snapshot/SPA divergence) vs. keep every item and collapse with CSS (no shift, crawlers unchanged). CSS chosen.
- **Where to store pins**: a `data` JSONB key (would be translated and copied, survives group changes) vs. a column next to `group_id` and `order_position`. Column chosen.

## Decision
1. Collapse only below 640 px, only groups with 4+ visible items, to a hand of 3 (revised: a swipeable deck of 2 tiles, see Revision).
2. Keep every item in the DOM, in group order, in both renderers; the hand is pure CSS (`data-preview="hand"`, `data-slot` on 3 items, percentage transforms), so the first paint on phones is already collapsed and the HTML for crawlers is unchanged in content and order.
3. JavaScript adds only state, the back tiles' `aria-hidden` / `tabindex` toggling, the pointer-only expand overlay's click handler, focus and a FLIP animation (transform/opacity, disabled under reduced motion).
4. Store pins as `content_items.pinned_in_group` (boolean), cleared whenever the stored `group_id` changes; pins reorder only the hand.

## Implementation
`packages/shared/src/section-preview.ts` (`SECTION_PREVIEW_SIZE`, `isCollapsibleGroup`, `previewSlots`, plus `groupSlug` (the anchor id, moved out of `GroupBlock` so the snapshot prints the same id), `groupDomIds` (`group-<groupId>-title` / `-items`) `tileDate` (day and full month name for the date cover) and `tileTint` (the cover's site tint)), `GroupBlock.tsx` + `hooks/useSectionPreview.ts`, `index.css`, `render-snapshot.ts`, migration `0015_content_pinned_in_group.sql`, `PATCH /api/admin/content/:id` (`pinnedInGroup`), admin toggle `GroupPinToggle.tsx` rendered from the group rows of `ContentPage.tsx`.

## Consequences
- No layout shift on phones and no SEO change; snapshot parity keeps comparing DOM order.
- Tile content is clipped (descriptions hidden, posters cropped) until the group is opened.
- A new column and a reset rule on the three write paths that change `group_id` (PATCH, restore, group delete); a future path that changes `group_id` must reset it too.
- Follow-ups: MCP pinning, expand analytics (spec 08 §11). The per-group opt-out shipped in the revision.
- Deviations from the original spec: (a) the snapshot sets `tabindex="-1"` only on the back tiles' links, not on the hidden items' content (those are `display: none` on phones, and `tabindex="-1"` on them would remove desktop keyboard stops before hydration); (b) collapsing animates the 3 hand tiles back, the other items disappear instantly instead of fading; (c) site labels are hidden inside tiles, like the description and CTA; (d) the "Doar primele 3…" hint (removed in the 2026-11-05 revision, when all pins started leading the deck); (e) a site switch resets groups to the hand (`GroupBlock` is keyed by site and group).

## Revision (2026-11-05): two-tile swipeable deck and per-group opt-out
User testing found the fan of three tiles hard to take in. The collapsing mechanism (CSS in both renderers, every item in the DOM, pin column, phones only, 4+ items) is unchanged; the presentation and interaction changed. Decisions 1 and 3 above are amended; decision 4 keeps its column but pins are no longer capped at 3.
1. **Deck of 2 tiles** instead of a fan of 3. The tile content is the original one (image or date cover, then the date and event-location rows, one line each cut with an ellipsis, then the title; description, CTA, glyphs and site label hidden; changed 2026-11-06 after testing: tiles with only image and title were too bare), shown as a top tile and a back tile (46 % of the list width, tilted -4° / +4°, back tile offset 68 % to the right, the cards of each pile peeking out under it, see point 3). `SECTION_PREVIEW_SIZE` is 2 and the collapse rule stays "more than 3 visible items" (`SECTION_PREVIEW_THRESHOLD`). Every item of a collapsible group is rendered as a tile in one shared grid cell, so all tiles take the height of the tallest one and the pair keeps one size while swiping; items outside the deck are `visibility: hidden`.
2. **Full-card deck tried and rejected.** An intermediate build showed the same full card component as the open list. After user testing it was dropped: short cards were either cropped to the height of a tall one or padded with empty space, so the deck never looked right across a mixed group. The tile helpers (`tileDate`, `tileTint`, `data-tile` markers, the `previewTile` prop, cross-fade copies on expand) were kept.
3. **Swipe through the whole group.** The deck is two piles and only one card moves (changed 2026-11-06 after testing: sliding the whole right stack and animating a new card in was too busy). Left pile: the top tile with the cards swiped past under it (`data-under="pile"`, most recent first, none before the first swipe). Right pile: the back tile with the rest of the deck order under it (`data-under="next"`). Real cards replace the fake `box-shadow` sheets (changed 2026-11-06 after testing): the first `SECTION_PREVIEW_DEPTH` = 2 of each pile show their edge as `data-depth="1|2"`, offset and rotated slightly from the pile's pose, never more than really remain (one edge at the penultimate card, none at the last); `deckUnder()` returns `{ pile: number[]; next: number[] }` and `deckLayer()` maps a tile to its pile and depth. Stacking is fixed, mid-drag too: top tile, left depth 1, left depth 2, back tile, right depth 1, right depth 2, parked tiles, with only the dragged tile above all (previously the revealed left tile sat under the back tile during a right drag and jumped on top on release). Swipe left moves only the back tile, in an arc onto the left pile, where it becomes the top tile; the next tile is revealed in place. Swipe left is optimistic (2026-11-06, after testing): the deck rearranges as soon as the tile is picked up, so the drop only lands it; a change of mind takes it back with the swipe-right tuck. Swipe right takes the top tile back onto the right pile (one step back) with a "tuck" (refined 2026-11-06): on release one continuous ~300 ms keyframe animation slides the tile about 28 % of a tile width past the right slot, above everything and clear of the new left top tile, then steps it down to the back tile's stacking (under the top tile, over the right pile) and slides it back into its slot under the top tile's edge (`SWIPE_TUCK_MS`, `SWIPE_TUCK_TURN`, `SWIPE_TUCK_CLEAR`); previously it stayed above the left pile and dropped under it in one frame. Reduced motion stays an instant swap. Every item of a collapsed group is parked in its pile's pose at z-index 0 on its own compositing layer (`will-change: transform`, `backface-visibility: hidden`), so a tile entering or leaving the deck changes neither transform nor layer as it shows or hides; role changes ease over about 180 ms (transform, plus a fade for tiles entering or leaving depth 2; hidden tiles fade out in place, then park; off under reduced motion); drag, landing and tuck share one transform function list, which fixed a one-frame unrotated flash on phones. At the start it just springs back. Deck order is all pinned items in group order, then unpinned; it does not wrap around (changed 2026-11-06 after testing): on the last item the top tile sits on the left pile, the right side is empty (no back tile, no `data-under="next"` tiles) and a further left drag springs back; `clampSwiped()` keeps the position within 0..count-1 and `previewSlots()` returns the top tile only. Underlay tiles are not clickable; the two visible layers per pile are `aria-hidden` and untabbable, and the snapshot prints the initial `data-under` / `data-depth`. Commit at 28 % of the card width or on a fling, otherwise it snaps back; vertical drags stay page scrolls (`touch-action: pan-y`). A visual-only "N / total" counter marks the position. State is JavaScript (`useSectionPreview.ts`, geometry mirrored in `SLOTS`); the first paint is still the CSS deck at tile 1.
4. **Taps:** only the top tile stays interactive. A tap on it outside its link, or anywhere on the back tile, expands the group, scrolls to and focuses that item; the back tile keeps `aria-hidden`, `tabindex="-1"` and the pointer-only `[data-hand-expand]` overlay. Expand and collapse run FLIP on the real cards from their deck pose (computed transform matrix) while inert copies of the two tiles cross-fade out.
5. **Per-group opt-out** as a column, for the same reason as the pin: `groups.section_preview BOOLEAN NOT NULL DEFAULT true` (migration `0016_group_section_preview.sql`), editable in the admin group dialog and carried to the public feed as `groupPreview` on each grouped item so the app and the snapshot agree (FR-115, BR-059). Rejected: a global setting (groups differ: a prayer-request list reads better as a list), and a per-site setting (the choice is about the group's content).

Consequences: swiping adds gesture code and a state beyond expanded/collapsed that resets on reload; keyboard and screen-reader users cannot swipe and expand with the button (unchanged); crawlers still see every item in order; tile content stays clipped until the group is opened; all tiles of a group share the tallest tile's height.
