# Business Rules

This file is the single source for business rules that must stay true regardless of implementation details. Requirements in `docs/product/requirements.md` link here rather than restating them.

## Rules
- BR-001: Content may belong to a specific church site or to the whole church.
- BR-002: Users must be able to access site-relevant content without losing the ability to view all church content.
- BR-003: Core information categories include events, important information, and bookmarked links.
- BR-004: Access paths should support both QR-code entry and direct-link entry.
- BR-005: When a group is scoped to specific sites, the entire group container (header and all items) is hidden for sites outside that scope. Group site scope takes precedence over individual item site scope. Items inside a site-scoped group are never visible on sites excluded by the group, regardless of their own site assignment. **Enforcement gap:** group `sites` are stored and editable, but `GET /api/content` does not yet filter by them (FR-008).
- BR-006: When a content item has `exclusive_site` set, it is hidden from the all-sites view (`GET /api/content` with no `?site=` parameter) and visible only when that specific site is selected (`GET /api/content?site=<slug>`). This is a hard visibility rule — the item does not appear in church-wide listings regardless of its `sites[]` array.
- BR-007: The `exclusive_site` column and the `sites[]` array are mutually exclusive on a single content item row. When `exclusive_site` is set, the server forces `sites = []` to prevent conflicting scoping semantics. The `sites[]` array continues to function as a surfacing hint (non-exclusive visibility) on rows where `exclusive_site` is null. Corollary: clearing `exclusive_site` (setting it to null via `PATCH /api/admin/content/:id`) requires an explicit `sites` array in the same request; the API returns 400 otherwise, because an exclusive row's stored `sites = []` would otherwise silently make the item visible to all sites.
- BR-008: Groups do not support the `exclusive_site` flag. An exclusive content item that belongs to a group will be hidden from the all-sites view at the item level — this can cause the group to render with fewer items in the all-sites view than in the site-specific view.

- BR-009: Duplicating a content item always creates a new item in `draft` state, regardless of the source item's state. Media attachment fields (`data.thumbnail` for cards, `data.imageUrl` for posters) are never copied — the duplicate starts with no image. All other `data` fields, site scope (`sites[]`, `exclusiveSite`), group assignment (`groupId`), and expiry (`expiresAt`) are copied from the source. The duplicate is appended at the end of the global item list and assigned to the same group as the original if applicable.
- BR-010: When a new content type is introduced that includes a media attachment field in its `data` JSONB payload, the `MEDIA_FIELDS` map in the duplicate endpoint must be updated to exclude that field from duplication. Failure to do so would silently copy a media URL reference without tracking it in the media library.

- BR-011: Short links are cascade-deleted when their parent content item is permanently hard-deleted from the database. Soft-deleting or archiving a content item does not affect its short links — they continue to exist and redirect visitors to the current destination URL. This ensures admins can temporarily hide content without breaking distributed short links (e.g. a QR code already printed on flyers).
- BR-012: The destination URL for a short link redirect is resolved dynamically at redirect time by reading the content item's current `data.link` value (or `data.siteLinks[siteSlug]` if a site override is configured on the short link). This means changing the content item's link automatically updates where all short links for that item redirect, with no need to update or re-create the short links. If the short link has a site override but the item has no `siteLinks` entry for that site, `data.link` is used. If no URL can be resolved (or the code is unknown), the redirect falls back to `/`.

- BR-013: Chronological ordering within a group uses `data.startDate` as the primary sort key and `data.startTime` as the secondary key (`eventSortKey()` / `compareEventSchedules()` in `@betel/shared`: ascending; on the same date, items without a time come before timed items). The same comparator orders dated items wherever the product lists them chronologically (feeds included). The sort is stable — items with the same startDate preserve their prior relative order. Items without a startDate are always placed after all dated items. When the sort button ("Sortează cronologic") is clicked on a group whose items are all undated, the action is a silent no-op and the order is unchanged. When a new item is created inside a group, the group is immediately re-sorted chronologically: the new item is treated as if appended last before sorting, so items with an equal startDate that already existed in the group remain before the new item. The "Sortează cronologic" button persists the resulting order via `PUT /api/admin/content/order`; on create, the server re-sorts and persists the group itself (`resortGroupChronologically` in `packages/api/src/services/group-order.ts`, used by `POST /api/admin/content` and the remote MCP `create_card`), loading the group's items ordered by `orderPosition` so ties keep the existing display order. Manual drag-and-drop ordering is unaffected and remains available as an alternative.
- BR-014: Expiry affects visibility only. Once an item's expiry condition is met (JSONB `startDate`/`endDate` or the `expiresAt` column — see `content-model.md` → Expiration Behavior and BR-015 for the day boundary), the item is excluded from the public hub, but its publishing state is not changed: a `published` item stays `published`. `archived` is set only by an explicit admin action. Automatic archiving on expiry is planned (FR-014) but not implemented.
- BR-015: Event dates and the time zone policy. `data.startDate` / `data.endDate` are calendar days written as `YYYY-MM-DD` (real dates; the API returns 400 otherwise). When both are set, `endDate` may not be before `startDate`; the admin API and both MCP surfaces check this on the item's resulting data (after a PATCH merge), so changing one end of the range is validated against the stored other end. An item with an event date stays visible through the **end of that day in Romania** (`Europe/Bucharest`) and is never hidden sooner for any visitor, editor or server time zone. A date-only `expiresAt` (`YYYY-MM-DD`) means the same thing (stored as the start of the following Bucharest day); a full timestamp is an exact instant and must carry `Z` or an explicit offset. Event dates and `expiresAt` apply independently: either one alone expires the item. Everything stored as a timestamp (logs, analytics, `expiresAt`) is UTC, and everything displayed is shown in the viewer's own time zone, chosen by the frontend. Rationale and mechanics: [ADR-017](../decisions/ADR-017-timezone-policy.md); expiry details: `content-model.md` → Expiration Behavior.
- BR-025: The event feeds show exactly the items the public hub shows for the same scope (same publishing-state, expiry and site-scoping rules, including BR-006), restricted to items with `data.startDate`. Any change to the hub's visibility rules must go through `listPublicContent` (`packages/api/src/services/public-content.ts`) so every server-side surface (hub JSON, feeds, server-rendered pages and structured data) stays in sync. See FR-060, ADR-021.
- BR-026: A feed item's `<link>` is always the item's canonical page `/i/<id>` (FR-069), identical in the all-sites feed and in every site feed. The item's external destination (`data.link` / `data.siteLinks`, resolved per the Link Resolution Rule — site override only in a site feed) is exposed separately as `betel:actionLink` and is never the `<link>`. See FR-061, ADR-021.
- BR-030: A content item is exposed as a schema.org `Event` only when it is a Card, is currently visible on the public hub (published, not expired per the Expiration Behavior — an in-progress multi-day event stays eligible until its last day), has `data.startDate`, and resolves to exactly one site (its `exclusive_site`, the site page being rendered, or a single-entry `sites[]`). Items that cannot be tied to one physical site (even when they carry a free-text `data.location`), and Richtext/Poster/Video items, are never marked up as events. The `Event.startDate` uses `data.startTime` when present (BR-035), otherwise the bare date. `Event.location` is a `Place` named after `data.location` (BR-050) when the card has one, otherwise after the resolved site, always carrying the site's `PostalAddress` and `containedInPlace` → the site's `Church`. Structured data is emitted only for entities visible in the server-rendered snapshot of the same page. Rationale: [ADR-022](../decisions/ADR-022-server-side-head-injection-and-content-snapshot.md); implementation: `packages/api/src/services/seo/page-model.ts`, `structured-data.ts`.
- BR-035: An event's start time (`data.startTime`, `HH:mm`, 24-hour) is a wall-clock time in `Europe/Bucharest` on `data.startDate`. It may exist only on single-day items (`startDate` set; `endDate` absent or equal to `startDate`); any write that would leave a time on a multi-day or undated item is rejected (HTTP 400 / MCP tool error), never silently dropped. Absent means all day or unknown, and consumers render the date only. The start time never shortens visibility: expiry remains governed by BR-015. Rationale: [ADR-023](../decisions/ADR-023-event-start-time-wall-clock.md).
- BR-040: Analytics date ranges in the range-based endpoints (`/api/admin/analytics/range`, `/items/:id/stats`, `/top-items`, `/short-links`) and in all MCP analytics tools are inclusive calendar days in the zone given by `tz` — an IANA name, `Europe/Bucharest` when omitted, invalid names and numeric offsets rejected — exactly as the other analytics endpoints (BR-015, ADR-017); a range spans at most 366 days and ends no later than today in that zone; the previous period is the equal-length window ending the day before `from`; the percentage change is computed per metric and is `null` when that metric's own previous-period value is 0 (the pre-existing dashboard endpoints keep returning `100`/`0` in that case). Implementation: `packages/api/src/services/analytics-range.ts`, `analytics-stats.ts`; ADR-024.
- BR-041: A short link can be created for any content item that is not `deleted` (drafts and archived items included). The label is 1–100 characters after trimming; the site override must be an existing site slug. Codes are 6 characters from `[a-z0-9]` and unique; generation retries on collision (up to 10 attempts on a unique violation). Every creation and deletion is audit-logged (`short-link.create`, `short-link.delete`) regardless of the path (admin UI, REST, MCP). Implementation: `packages/api/src/services/short-links.ts`; FR-083.
- BR-050: A card's location (`data.location`) is optional plain text of 1–70 UTF-16 code units after normalisation (control characters stripped, whitespace collapsed, trimmed). Every write path — the admin API (on the resulting type and data, so a type change away from card cannot keep a location), the translation API, both MCP surfaces and the AI translation job — applies the same rule: `null` or an empty value means "no location" and removes the key; non-strings, over-long values and non-empty locations on non-card items are rejected (HTTP 400 / MCP tool error; the AI job drops and logs). A stored location is therefore always non-empty. It is never interpreted as Markdown or HTML and never rendered as a link. Implementation: `packages/shared/src/event-location.ts`, `packages/api/src/services/event-location.ts`.
- BR-051: The location is translated per locale like title, description and CTA, with Romanian fallback when a translation has no value. Translated values obey BR-050 (same normalisation, same bound, empty removes the key); the AI translation job discards any that do not, so the fallback applies instead of an invalid value.
- BR-052: Public cards render a present location as its own metadata row directly below the date/time row (or in its place for undated cards) with a map-pin glyph in the text colour and a screen-reader label (`location.label`); other content types never render it.
- BR-053: The location is a human-readable place name only. It never affects visibility, site scope, expiry, ordering or notification targeting; the site remains the entity for those. Consumers that name a place (today the RSS feed's `where` line and `ev:location` and JSON-LD `Event.location.name`; the notification body and link-preview description when those features ship) prefer the location over the site name when present and fall back to the site otherwise; postal addresses always come from the site.
